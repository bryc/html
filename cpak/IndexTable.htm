The IndexTable

The IndexTable is a 256-byte data structure that addresses where and in what order a file's data segments should be read (aka "pages"). The IndexTable is divided into 128 IndexNodes, and each node is a direct representation of a segment of the entire memory contents, in this case 32768 bytes. So for example, the 6th node represents the allocation state of one specific 256-byte data segment starting at address 0x500. This points to the earliest available segment in which user save data can be stored. The initial 5 segments before this are reserved for the filesystem itself. This is how we end up with a total capacity of "123 pages".

The value of an IndexNode tells us one of 3 things:

  1. If 3: Next available segment (i.e. unused; available for use)
  2. If 1: Final segment of the IndexChain
  3. A value 5-127: The next segment of a chain
  4. Any other value: Outside range (Invalid)
This basically means that each file allocation is represented using the Linked List data structure (though I prefer just calling them chains). Note that the IndexTable itself does not explicitly define the start index of the chain. These values are stored in a separate data structure: the NoteTable ("notes" are essentially just N64 terminology for "files" in this filesystem).

This is bad, because without context, it's not obvious that index 5 is the correct startIndex. And there's no way to be 100% sure if this is an error. A heuristic such as checking if the nextIndex is less than the previous could in theory help, but it would not work in all cases, and technically, going in reverse or random order is "legally possible", but it actuality, this does not occur in typical use. We may also use the checksum, but this requires the checksum itself to be correct, and this will just tell the code to use the backup, which could potentially ignore valid data in the primary.

This is why it's essential to have the startIndexes explicitly defined, in this case, in the NoteTable.

The Backup IndexTable

There is in fact a backup of the IndexTable, essentially intended to be a 1:1 copy of the primary IndexTable. The Primary IndexTable is actually stored at index 1 (again, counting from 0), and the Backup is stored at index 2. Though in the case of filesystem offset locations it's more appropriate to use their real addresses in memory: 0x100 and 0x200.

Put simply, whenever the IndexTable is modified, either deleting a file, or writing one, the result is then copied to the backup. But if the Primary IndexTable checksum ever fails, the backup will be restored, at least in libultra games.

In fact, in libultra, even if the backup were to be empty, as long as the checksum is correct, it will be copied to the primary, even if the only invalid data in the primary was the checksum. So this hypothetical scenerio would lead to data loss by trying to avoid data loss.

Parsing and Repairing an IndexTable

If you've played the N64 enough, especially with a third party C-Pak, you've likely encountered a C-Pak error screen, telling you it's "damaged", and asks if you want to "attempt repair". Almost every N64 game utilizes the same standard SDK library, known as libultra. And somewhere in that library contains code for the C-Pak that can repair some problems in the IndexTable. It does an OK for what it is, but it's not optimal. It's not as flexible as it could be. But I don't blame them, the logic required to optimally retain as much valid data while repairing as much as possible, can end up quite complex. Things will likely get quite technical after this point, so fair warning.
